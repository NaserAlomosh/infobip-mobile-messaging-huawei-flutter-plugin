## Remaining production risks and compatibility decisions

- **Inbox setSeen persistence: UNRESOLVED.** The existing Huawei `MobileInbox.setSeen(externalUserId, messageIds, listener)` remains unchanged. Native success does not prove read-after-write persistence. No JWT or speculative authentication change was added.
- **RTC: unsupported for Huawei-only production.** No supported narrow replacement/manifest-only path was established for RTC 15.1.0's reachable Firebase bridge. The conflicting standard core was not restored. Future support requires a supported transport/packaging architecture and real device verification. The retained reflection adapter and its lifecycle tests are dormant, not proof of working calls.
- **RTC lifecycle limits:** SDK registration has no public cancellation API. In the retained adapter, teardown waits for a delayed enable result before unregistering the actual handle; without a callback it can remain pending. Failed disable retains the handle for retry. Engine detach initiates best-effort teardown and cannot report a Flutter result. Production entry points are currently gated.
- **Custom attributes:** CustomList accepts Huawei's flat scalar records with consistent fields/types, not arbitrary nested JSON. Native calendar Date values are `YYYY-MM-DD` strings; Dart DateTime writes remain tagged instants. Huawei list records erase date type metadata into their stored date/ISO strings; returned records preserve those strings and backend values, not an invented nested type tag. Ordinary strings stay strings. See README and actual native regression tests.
- **Intentional API alignment:** `depersonalizeInstallation` now returns `Future<void>`; `setInstallationAsPrimary` returns `Future<List<Installation>?>`. Consumers depending on the former list result must adapt. InboxMessage is a dedicated Message subtype with topic/seen/sentTimestamp and rich content retained. No version bump was made.
- **Tap replay:** memory-only latest pending tap, delivered once when a Dart event sink attaches, cleared by cleanup. It is not a persistent queue. Robolectric tests use real SDK broadcasters but simulate system receiver delivery; manifest/cold-process behavior still needs device validation.
- **Release rules:** exact optional-class suppressions apply to the inspected, pinned Huawei graph. They do not provide absent runtime implementations or prove fallback behavior on every OEM device. The detailed per-class binary assessment is in `docs/android-release-verification.md`.
- **Configuration:** a host must own its real Huawei numeric `app_id`, matching AppGallery Connect setup. Validation rejects the fake placeholder but does not prove a real ID belongs to a project or that HMS registration succeeds.
- The analyzer remains nonzero because of existing deprecation information notices. Vendor build warnings remain. These were not broadened into unrelated cleanup.
