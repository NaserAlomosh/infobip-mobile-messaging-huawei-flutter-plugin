# Final example configuration and authentication audit

Audit dates: 10–11 October 2026 (Asia/Amman). Branch: `feature/huawei-rtc-core`.
Starting/current HEAD: `4367f0cfce8391bf052052975ac7c0e449197305`.
No pre-existing tracked/untracked changes were reported by Git at entry. Ignored local config and launcher existed, matched the empty template/mapping, and were not tracked. No local credential values were printed or changed.

## Findings

| Classification | Area | Evidence / outcome |
| --- | --- | --- |
| CONFIRMED | Static mapping | `main.dart` maps every static field into `ExampleConfig`; `main_local.dart` has the identical mapping with only its config import changed. `prepare_local.dart` copies an absent local config and never overwrites existing values. All active feature routes share the injected controller; no runtime mock identity or duplicate credentials were found. Full restart/rebuild is required for static changes. |
| CONFIRMED | Local/clean entrypoints | Plain `flutter run` uses the tracked empty template. `flutter run -t lib/main_local.dart` uses the ignored local Dart file. Config, entrypoint and AGC file are ignored and untracked. No missing local import appears in the tracked application's import graph. |
| NOT_APPLICABLE | Legacy independent RTC credentials | Legacy Package A authorization KID/hex secret map to `jwtKid`/`jwtSecretKey`; Application Code maps to `infobipApplicationCode`. Legacy Package B's Application ID, AppKey and Base URL are not inputs to the new outgoing extension. No old package, initialization or decryption was introduced. `environmentName` is injected but is not consumed by SDK requests or reports. |
| CONFIRMED | Initialization | Application Code is trimmed and passed to public `initialize(applicationCode:)`; the initialized flag is set only after native success. Repeated initialization is idempotent. Installation ID, token, enabled flags and permissions are separate readiness checks; initialization does not prove registration. |
| FIXED | Initialization/error status | Missing Application Code now produces an explicit local blocker. Initialization failure retains its sanitized SDK diagnostic in the catalog rather than being replaced by a generic `StateError`. |
| CONFIRMED | Generated MM JWT | Existing helper is unchanged: HS256, JWT header, KID, Bearer claim, unique secure UUID-v4 JTI, configured trimmed subject/Application Code issuer/API-key claim, integer issued/expiry times, hex-decoded key bytes and validated TTL. No global token caching or secret logging. Existing byte/signature/freshness tests pass. |
| FIXED | Supplied JWT validation | Previously only `sub`/`exp` were checked; malformed header, absent mandatory claims and wrong MM issuer could pass local readiness, and missing `iat` later failed metadata decoding. Now check required MM versus Chat headers/claims separately, canonical identity, times, issuer/key identifiers when configured, and compact HS256 signature shape. MM requires its Application Code issuer/API-key claim. Chat permits the documented omitted-exp default of `iat + 15`. These are structural checks, never claims of verified signatures. |
| FIXED | Test identity / User controls | The old User screen saved `_user?.externalUserId` and cached contacts. It now uses the configured trimmed identity and configured contacts in both catalog and controls, retains unrelated fields only from the same identity, and fetches the server after writes. Fetched private names no longer overwrite visible test inputs. Get/fetch inspect the SDK's current installation user; their API has no external-user parameter. No identity is silently generated. |
| FIXED | Personalization / depersonalization | Catalog, setup and User controls use shared guarded paths. Personalization retains the configured identity and now fetches server state after the callback. Configured names are supplied by the profile controls; setup's existing identity-only call remains identity-only. Depersonalization fetches the server afterwards. Missing identity blocks writes. Active calls block mutation; prepared Chat blocks identity switching until restart, rather than silently invalidating its provider/session. |
| CONFIRMED | Inbox auth/API mapping | Application Code mode awaits `setJwt(null)` and aborts fetch if clearing fails. JWT mode passes a fresh generated token, or a still-valid supplied token, through `fetchInbox(jwt:, externalUserId:, options:)`. Both require SDK initialization. Topic/limit/counters and seen/re-fetch use supported arguments. No JWT argument was added to set-seen. |
| FIXED | Inbox report mode | A row previously captured the old auth selection before switching to its named mode. Selection now precedes recording, so JWT rows record JWT. Missing identity/limit/signing requirements and missing negative-test identity produce specific blockers. |
| CONFIRMED | Native MM JWT scope | Native `SET_JWT` dispatches to `InboxManager.setJwt`; explicit/global Inbox token precedence is implemented there. User methods have no JWT argument and the example does not invent a global user-auth mode or claim that its Inbox JWT authenticates User APIs. |
| CONFIRMED | Chat helper/provider | Separate widget issuer, Base64 secret, HS256 header, `ski`, `stp=externalPersonId`, unique JTI, matching personalized subject and TTL. Generated helpers sign on each provider callback; installation mode installs no JWT provider and there is no fallback from JWT mode. Existing Chat send/reconnect bridge and public SDK behavior are unchanged. |
| FIXED | Chat readiness/errors | AUTH's Chat-JWT row no longer runs successfully under installation mode. Specific missing Chat requirements appear as Blocked. Provider errors (including expired supplied tokens/invalidated identity) now use the public `onError` hook to show sanitized diagnostics, while native rejection still occurs. |
| CONFIRMED | RTC contract / unchanged implementation | Calls configuration ID and optional explicit identity reach `HuaweiRtc.callApplication`; empty identity uses registered installation push ID through native `HuaweiRtcTokenProvider`. Native `MobileApiResourceProvider` issues the token for `TokenBody(subject, 43200L)` and passes it directly to Core. Audio/video type, hangup, active snapshots, permission checks, event stream and stable errors use the existing branch APIs. No RTC implementation or safeguard was edited. Incoming HMS and preview/remote renderer remain unsupported. |
| FIXED | Catalog status correctness | All 71 rows remain mapped to real public operations, existing feature controls, explicit manual scenarios or the two unsupported rows. Missing local prerequisites now block before execution. Unexpected operation failures produce Fail; intentional rejection tests require manual confirmation. Blocked/unrun/unsupported rows and unexpected failures cannot be promoted to Pass without an eligible re-run/confirmation state. Successful SDK callbacks still never auto-pass. |
| FIXED | Persistence | Previously restart restoration discarded actual/error evidence and could overwrite a newly begun row. The private app-generated sanitized evidence is now restored; startup writes await restoration, and new local results win over the older snapshot. Interrupted RUNNING rows become REQUIRES_MANUAL_VERIFICATION, not Pass. Restored results are historical; rerun after changing user/profile/configuration. |
| FIXED | Safe diagnostics | Numeric SDK service codes were formerly collapsed to `operation_failed`. Bounded numeric codes and known stable codes now remain visible, while raw native messages/details/headers/tokens remain omitted. Reports use recognized auth labels rather than arbitrary config text. |
| CONFIRMED | Secret protection | No raw JWT/key/Application Code/push/RTC token is written to test reports or event logs. App-owned match flags, counters and sanitized errors are used; local secrets remain ignored. Tests use synthetic fixtures only under `example/test`; none enter device execution. Native Chat necessarily displays test conversation content, so keep device screenshots private. |
| UNVERIFIED | Existing upstream diagnostics risk | Repository RTC documents identify upstream Huawei SDK AuthorizationUtils header logging. This audit did not capture real SDK logs, modify vendor/production code, or establish that external runtime diagnostics are secret-free. |
| UNVERIFIED | Backend/Huawei acceptance | Real registration, authorization, personalization persistence, Inbox seen-context equivalence, Chat reconnection/attachments/provider acceptance and peer RTC media require actual Portal/device tests. A supplied token's signature/key ownership and an unspecified Chat issuer's Portal association are backend checks. A static supplied JWT cannot renew itself on expiry. |
| UNVERIFIED | Pending RTC identity switching outside catalog | `getActiveCall()` is documented to return null during token acquisition; no authoritative public pending-call state exists. Running catalog RTC rows and native active snapshots are guarded, but a pending request opened through older direct controls cannot be inferred from a null snapshot. Finish the call attempt, hang up/await finished, and run User changes before RTC. No false guarantee or RTC modification was added. |
